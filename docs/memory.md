# Project Memory — Decisions, Reasoning, Fixed Bugs

Fast-reference for a new contributor or a fresh AI session — read this before re-deriving something the hard way.

## Why Airtable instead of a traditional database

There is no Postgres/Mongo/etc. anywhere in this project. Airtable is the entire CMS backend, queried via raw `fetch()` to its REST API (no SDK dependency). Every API route that reads Airtable has a hardcoded fallback (`DEFAULT_CONTACT`, `DEFAULT_SETTINGS`, `DEFAULT_PACKAGES`, `fallbackProjects`, `preWrittenReviews`) so the site keeps working even if Airtable is unreachable or unconfigured. This is a deliberate low-ops choice for a small studio site: the owner edits content through the admin dashboard (or Airtable's own UI directly) with zero database migrations, zero hosting, zero backup strategy to maintain.

## Why client-side-only processing for the Free Tools

Every tool that processes media (trim, mix, denoise, vocal-remove) runs entirely in the browser — `ffmpeg.wasm` for audio operations, `onnxruntime-web` (WASM) for the ML-based vocal separation. This means the marginal cost of a tool going viral is $0 in server compute, at the cost of the browser doing real work (sometimes tens of seconds to minutes for the heaviest tool). This tradeoff was made deliberately, not by default — see the Vocal Remover model-selection story below for how far this constraint was pushed.

## Why Git LFS was adopted (and how)

Vocal Remover needed two large binaries: a 67MB ONNX model (`Kim_Vocal_2.onnx`) and a 14MB `onnxruntime-web` WASM runtime file. Pushing them as regular git objects failed — not because of a client-side buffer-size limit (that was the first guess and it was wrong: `http.postBuffer` was already generously set to 500MB before anyone touched it), but because **GitHub enforces an ~90-second server-side timeout on `git-receive-pack`**, and the actual upload bandwidth on the connection involved (~237-270 KB/s) couldn't finish sending the ~62MB pack before that timeout hit — confirmed via `GIT_CURL_VERBOSE` tracing showing an `HTTP 408` after the connection had transferred only ~23MB.

Git LFS's chunked, resumable upload protocol isn't subject to that single-request timeout, so it succeeded on the identical slow connection where the monolithic push failed.

**Important nuance if this comes up again**: the two files were already committed as regular blobs before the LFS decision was made. `git lfs track` alone does *not* retroactively convert already-committed files — it only affects files added after tracking starts. The actual fix was `git lfs migrate import`, scoped precisely to the two files' paths (explicitly excluding `public/ffmpeg/ffmpeg-core.wasm`, a ~32MB file that happens to already be committed as a regular git object in older, already-pushed history — migrating that would mean rewriting shared history other people/deployments depend on, which needs explicit buy-in first). `git lfs migrate` only rewrites commits that don't yet exist on any remote by default, which made it safe here since the vocal-remover commit was still local-only at the time.

**A snag worth knowing about**: right after running `git lfs migrate import`, the working-tree copies of both files were left as ~130-byte LFS pointer text (not real binaries) — the automatic smudge didn't happen. The real data was safe in the local LFS cache the whole time; `git lfs checkout` restored it. Verify with `md5sum` against a known-good hash if you're ever unsure whether a working-tree file is a real binary or an unresolved pointer.

**Vercel doesn't automatically resolve LFS pointers** unless "Git LFS Support" is enabled in the Vercel project's Git settings — this is a dashboard toggle, not something fixable from a git push alone. `scripts/vercel-build.sh` (wired via `vercel.json`) is a build-time safety net: it retries `git lfs pull`, then checks the resolved file sizes are above a sane threshold (not ~130 bytes) before letting `next build` run — so a broken LFS checkout fails the deploy loudly instead of silently shipping a broken `.onnx`/`.wasm` file to production.

## Notable bugs fixed

**Hero section: floating icons rendering on top of the founder's face.** Root cause: `components/site/Hero.js`, the founder-photo wrapper `<div>` had `zIndex: 2` in its inline style but no `position` property — CSS only honors `z-index` on positioned elements, so it was silently ignored (defaulted to `position: static`). Meanwhile the floating-icons container genuinely had `position: absolute; z-index: 1`, so it always painted on top regardless of the intended `2 > 1` order. The original author's own code comment (`/* Emerges from behind the founder (z-index 2) */`) confirms the intent was always correct — the implementation just never worked. Confirmed via git history that this bug existed since the very first commit; it wasn't a regression from recent work, just something that became visually obvious at some point. Fix was one line: add `position: "relative"`.

**CSP blocked WASM compilation in production only.** `onnxruntime-web`'s `WebAssembly.instantiate()` call was blocked by the site's CSP in production, but worked fine locally — because Next.js dev mode's CSP includes the broad `'unsafe-eval'`, which also happens to cover WASM compilation, masking the issue until a real production deploy. Fix: added `'wasm-unsafe-eval'` (the CSP3 keyword scoped specifically to WebAssembly, not general `eval()`) to `script-src` unconditionally, not just in dev. **Lesson: always test CSP-sensitive changes against a real `next build && next start`, not just `next dev`.**

**Vocal Remover main-thread blocking / Chrome "Page Unresponsive" dialog.** The STFT/ISTFT/inference pipeline was originally running on the main thread; on anything longer than a few seconds of audio, this blocked the UI hard enough to trigger Chrome's unresponsive-page warning. Fixed by moving the entire separation pipeline into a dedicated Web Worker (`lib/vocal-remover/separation.worker.js`), keeping only audio decode (needs `AudioContext`, unavailable in workers) and the final MP3 encode (ffmpeg.wasm already runs in its own worker internally, so it was never the actual problem) on the main thread. Verified the fix by polling `page.evaluate()` responsiveness every 200ms through an 18-second clip's full processing run — max latency 23ms, versus the multi-second blocking stalls before.

## The Vocal Remover model story (worth knowing if you touch this tool again)

The original ask was "Demucs" specifically, but true Demucs ONNX exports found publicly were either an unverified 316MB file from a low-trust source (a brand-new HuggingFace repo, 1 like, published by a commercial API vendor promoting their own product) or not size-appropriate. The model actually shipped is **Kim_Vocal_2.onnx**, an MDX-Net architecture model from the well-established Ultimate Vocal Remover (UVR) project — same practical outcome (vocal/instrumental separation), right-sized (67MB vs the target ~150MB budget), and from a source with years of real-world production use. Its exact STFT/inference config (`n_fft=7680`, `dim_f=3072`, `compensate=1.009`, etc.) was not guessed — it was pinned by computing the file's MD5 hash using UVR's own actual hashing scheme (MD5 of the **last 10,000KB** of the file, not the whole file — a detail found by reading UVR's own source, `get_model_hash()` in `UVR.py`) and cross-referencing UVR's `model_data.json`. The STFT/ISTFT JS port was verified numerically against a Python/numpy + onnxruntime reference before being trusted (relative RMS error ~1e-7 on the STFT, ~2e-8 on the full pipeline).

If a future "Hinglish subtitle generator" or similar ML-based tool gets built, expect a similar model-sourcing exercise: verify the actual file hash/provenance, don't trust a model's name or a single source's claim, and numerically validate any hand-ported DSP/preprocessing code against a reference implementation before shipping it.

## Things a new contributor should know immediately

- **Firebase is currently dead weight.** `firebase`/`firebase-admin` are real dependencies with real init code (`lib/core/firebase.js`, `lib/core/firebase-admin.js`), and `firestore.rules`/`storage.rules`/`firebase.json` exist at the repo root — but nothing in the app actually calls Firestore, Storage, or Firebase Auth. The only remaining trace is a decorative, non-functional "Firebase Connected" status badge in the admin dashboard UI. Admin auth is a custom JWT scheme, not Firebase Auth. Don't assume Firebase does anything until this is either finished or removed — check before building on it.
- **No root `middleware.js`/`middleware.ts` exists.** Admin route protection is manual, per-API-route (`isAuthenticated(request)` called inside each handler individually), not centrally enforced. Two admin GET routes (`/api/admin/portfolio`, `/api/admin/contact`) are currently *not* gated at all. The dashboard page itself is a client component that redirects only after an async auth check resolves — the page's JS ships before that check completes.
- **`components/*.js` and `lib/*.js` top-level files are re-export shims**, e.g. `components/Hero.js` is one line: `export { default } from "./site/Hero";`. The real implementation is under `components/site/` and `lib/core/`. If you're editing and the file looks suspiciously empty, check for this pattern before assuming something's broken.
- **Two of the largest binaries in `public/` are *not* LFS-tracked** despite being comparable in size to the ones that are: `public/ffmpeg/ffmpeg-core.wasm` (~32MB) and `public/audio-models/std.rnnn` (~300KB, smaller but still worth noting). This works today only because that particular push happened to succeed — it's a latent risk if either file ever needs to change.
- **`wavesurfer.js` is a declared dependency that isn't actually used** — the custom waveform UIs (`SimpleWaveform.tsx`, `WaveformTrack.tsx`) are hand-built, not wrapping the library. Don't assume importing from `wavesurfer.js` will find existing usage patterns to follow.
- **The lead-gen WhatsApp CTA is inconsistently applied** across the Free Tools — see `PRD.md`/`rules.md` for exactly which tools have it and which don't. Don't assume a tool has it just because "every tool should."
